# Lab3 实验报告：RISC-V 中断与异常处理


## 一、对本章整体逻辑线的理解

对本章的任务理解为：让内核在执行流被中断或异常打断后，能够接管处理，并在处理结束后正确继续执行。仅仅让 CPU 跳到某个入口还不够，入口之前的状态必须能够保留下来，处理函数必须得到正确的上下文，最后还必须按照处理结果恢复执行位置。

本章围绕三条主线展开。第一条是 Trap 上下文保存与恢复，它回答“被打断的程序状态放在哪里、如何取回来”；第二条是 Trap 入口与返回，它回答“如何从硬件入口进入 C 函数，再从 C 函数回到原程序”；第三条是中断与异常处理，它回答“进入内核后究竟要做什么、返回前需要修改哪些状态”。

实现顺序先解决底层上下文，再建立汇编与 C 的接口，最后编写具体处理行为

### 1. 初始化：建立可以接收 Trap 的运行条件

内核从 `kern/init/entry.S` 进入，建立启动页表和内核栈，随后执行 `kern_init()`。本次首先补回实验2中的物理页初始化和 Best-Fit 实现，使已有的内存管理初始化、自检能够完成。本实验最终仍使用框架默认的 First-Fit，Best-Fit 在临时测试副本中单独验证。

随后，`idt_init()` 将 `sscratch` 清零，并把 `__alltraps` 的地址写入 `stvec`。这里的具体机制是 RISC-V 的 `stvec` 直接入口，并没有建立 x86 式的中断描述符表。当前框架在 `kern_init()` 中调用了两次 `idt_init()`，本次保留了该结构。

`clock_init()` 在 `sie` 中打开时钟中断使能位，设置第一次时钟事件，并将 `ticks` 清零。最后，`intr_enable()` 设置 `sstatus.SIE`，允许当前 S 模式接收已使能且满足条件的中断。因此，“设置入口”“使能特定中断源”“打开当前级别的中断总开关”是不同步骤。

### 2. Trap 发生：硬件记录控制信息，软件保存通用寄存器

在本实验的 S 模式 Trap 路径中，处理器通过 `sepc`、`scause` 和相关状态位记录返回位置、原因与返回状态，再将控制流交给入口。硬件并不会自动把全部通用寄存器压入内核栈；这部分由 `SAVE_ALL` 。

进入 S 模式 Trap 时，原 SIE 被记录到 SPIE，SIE 清零，SPP 记录原特权级；`sret` 再按照 SPIE、SPP 恢复相应的中断使能与返回级别。因此，帧中的 `status` 保存的是进入 Trap 后的状态，Trap 前的使能信息通过 SPIE 保留，不能理解成所有状态位都与进入前相同。这也是本实验恢复保存的 `sstatus` 后仍能安全完成余下寄存器恢复的原因。

本次测试主要打断正在 S 模式运行的内核，因此发生 Trap 时不一定存在 U 到 S 的特权级切换。

### 3. 处理与返回：保持状态的一致性

`SAVE_ALL` 建立 TrapFrame 后，`__alltraps` 将帧地址传给 `trap()`。`trap_dispatch()` 根据 `cause` 的最高位区分中断与异常，再进入对应处理函数。

时钟中断需要设置下一次事件、更新计数并按条件输出和关机。非法指令与断点异常需要输出信息，并调整帧中的 `epc`，使返回后跳过本实验要求忽略的故障指令。处理函数返回后，`__trapret` 调用 `RESTORE_ALL`，最后执行 `sret`。

整个过程可以表示为：

```text
设置 stvec、时钟事件和中断使能
        ↓
Trap 发生，硬件记录控制信息
        ↓
__alltraps → SAVE_ALL → 建立 TrapFrame
        ↓
a0 = 当前帧地址 → trap(tf) → trap_dispatch(tf)
        ↓
interrupt_handler(tf) 或 exception_handler(tf)
        ↓
__trapret → RESTORE_ALL → sret
        ↓
恢复原执行流，或从处理后指定的 epc 继续执行
```

## 二、核心函数与功能模块的理解

### 1. `struct trapframe`：汇编与 C 共同遵守的数据布局

`kern/trap/trap.h` 中的 TrapFrame 包含 32 个通用寄存器槽位及 4 个控制信息字段。RV64 下每个槽位是 8 字节，总大小为 `36 × 8 = 288` 字节。

| 槽位 | 字节偏移 | 对应内容 |
| --- | --- | --- |
| 0 | 0 | x0，固定为零 |
| 1 | 8 | x1，即 ra |
| 2 | 16 | x2，即 Trap 发生前的 sp |
| 3–31 | 24–248 | x3–x31 |
| 32 | 256 | status，对应保存的 sstatus |
| 33 | 264 | epc，对应保存的 sepc |
| 34 | 272 | badvaddr，对应旧名 sbadaddr、现名 stval |
| 35 | 280 | cause，对应保存的 scause |

TrapFrame 是一个接口约定。汇编中的保存偏移、恢复偏移和 C 结构体布局必须完全一致。如果 C 中把某个字段解释成 `epc`，汇编却把该偏移当成普通寄存器，程序就可能返回错误地址。

### 2. `SAVE_ALL`：保存上下文，特别处理 sp

`SAVE_ALL` 是框架已有实现，本次未修改。它先把原 sp 放入 `sscratch`，再将 sp 减去 288 字节，为当前帧分配空间。除了 x2，它先保存其他通用寄存器，然后通过 `csrrw s0, sscratch, x0` 取回原 sp，同时将 `sscratch` 清零，最后把原 sp 存到槽位 2。

这解释了为什么 sp 不能与其他寄存器机械地采用相同保存方式：完成栈空间分配之后，当前 sp 已经变成帧地址，原 sp 必须从预先保留的位置取回。

`SAVE_ALL` 读取 CSR 时使用 s0–s4 作为临时寄存器，但这些寄存器的原值已经提前保存在帧中，因此不会丢失被打断程序的对应状态。

### 3. `RESTORE_ALL`：恢复顺序是正确性的一部分

本次实现先从槽位 32、33 读取并恢复 `sstatus`、`sepc`，随后恢复 x1、x3–x31，最后才恢复 x2。

先恢复 CSR，是因为这里需要使用 s1、s2 作为临时寄存器。如果先恢复它们的原值，再用来读取 CSR，这两个寄存器就会再次被覆盖。最后恢复 sp，则是为了让前面所有读取操作仍以当前 TrapFrame 为基址。

本实现直接采用帧中保存的原 sp，而不只把当前 sp 增加固定长度。这样恢复语义与 `SAVE_ALL` 的槽位关系保持一致。`cause` 和 `badvaddr` 用于分类、诊断，本实验返回路径不需要把它们重新写回 CSR。

### 4. `__alltraps`、`trap()` 与 `__trapret`：连接两种执行环境

建立好帧后，入口执行：

```asm
mv a0, sp
jal trap
```

这两条指令将当前帧地址作为第一个参数传给 `trap(struct trapframe *tf)`。这里依赖整数调用约定中的 a0 参数寄存器；帧大小 288 又是 16 的整数倍，因此在原栈满足标准对齐要求时，调用 C 函数仍保持对齐。

`jal` 会修改 ra，但被打断程序的 ra 已由 `SAVE_ALL` 保存。C 函数按照调用约定恢复自己的栈后，控制流回到紧接其后的 `__trapret`。此时 sp 再次指向 TrapFrame，可以开始恢复。

C 函数返回是从处理函数回到汇编调用点；`sret` 才是按照恢复后的特权状态和 `sepc` 完成 Trap 返回。当前实现没有修改 `trap()`、`trap_dispatch()` 的逻辑或函数签名。

### 5. `interrupt_handler()`：分类、重设时钟与计数

`trap_dispatch()` 使用有符号解释下的 `cause` 是否为负，判断最高位是否置位。进入 `interrupt_handler()` 后，再屏蔽最高位以取得实际中断编号。这样才能把 `0x8000000000000005` 识别成 `IRQ_S_TIMER`，而不是直接将整个位模式与数值 5 比较。

对 S 模式时钟中断，处理顺序为：调用 `clock_set_next_event()`，执行 `ticks ++`，然后检查是否达到 100 的整数倍。达到时调用已有的 `print_ticks()`，同时增加统计输出次数。输出达到 10 次后，调用 `sbi_shutdown()`。这里 `ticks` 统计中断次数，静态变量 `num` 统计输出次数，两个计数器的单位不同。

其他已定义的软件、时钟和外部中断只输出类型提示，未知类型输出原因并调用 `print_trapframe(tf)`。

### 6. `clock_set_next_event()` 与 `intr_enable()`：提供触发条件

`clock_set_next_event()` 读取时间计数，并通过 `sbi_set_timer()` 设置后续事件。框架当前采用“当前时间加固定增量”的方式，每次处理时重新设定。

`clock_init()` 打开时钟源的使能位，`intr_enable()` 打开 S 模式中断总使能。

### 7. `exception_handler()`：输出之后决定如何继续执行

本次对非法指令和断点分别打印 `Illegal instruction at 0x…`、`Breakpoint at 0x…`，然后读取 `epc` 所指指令的首个 16 位。在本实验使用的 16/32 位编码范围内，低两位为 `11` 时将 `epc` 增加 4，否则增加 2。

这使处理代码同时支持 2 字节的 `c.ebreak` 和 4 字节的 `ebreak`，也能处理本次测试中的两种长度非法编码。若不更新 `epc`，返回后会再次执行同一条故障指令；若固定增加 4，则可能跳过压缩指令之后本来应该执行的内容。

## 四、AI 辅助实现中遇到的问题及解决过程

### 1. 骨架与实验2依赖未完成，首次编译不能通过

最初编译时，`trap_dispatch()` 调用的两个处理函数尚未定义，编译器报告 `implicit declaration of function 'interrupt_handler'` 和 `exception_handler`。同时，框架中的 `page_init()` 与 Best-Fit 实现也留有实验2填空。

解决时先按本实验接口补全两个处理函数，再从已有实验2代码中提取必要实现。实验2与实验3的常量命名不同，因此将原先的物理边界常量转换为 `KERNTOP - PHYSICAL_MEMORY_OFFSET`、`KERNBASE - PHYSICAL_MEMORY_OFFSET` 等当前框架可用表达式。移植过程中保留了实验3已有的中断保护接口，避免整文件覆盖。

这说明提示词需要明确“依赖哪些已经存在的实现”，否则 AI 即使把本章填空写完，也可能留下无法构建的前置缺口。

### 2. 旧 CSR 名称导致汇编失败

首次构建还出现了实际错误：

```text
Error: unknown CSR `sbadaddr'
```

错误位于框架提供的 `SAVE_ALL`，而本实验约束不允许修改该宏。当前汇编器接受 `stval`，因此通过本地构建脚本给编译器加入 `-Dsbadaddr=stval`，让预处理阶段完成名称兼容。这样保留了源代码中的保存布局，也没有把工具链兼容问题混入 Trap 恢复逻辑。

改进后的任务约束是：遇到构建错误时，先确认它属于 ISA 逻辑、框架接口还是工具链命名差异，再选择修改位置。

### 3. 编译通过后，QEMU 只显示固件信息

完成主要填空后，QEMU 曾经只能输出 OpenSBI 横幅，无法进入 C 初始化。结合启动代码检查发现，根页表只映射了高位内核虚拟地址，没有保留启动阶段当前物理 PC 的映射。执行 `csrw satp` 开启分页后，后续指令仍位于物理地址附近，尚未完成跳往高地址的过程。

解决方法是沿用实验2中的必要修复，在根页表第 2 项增加从 `0x80000000` 开始的 1 GiB 恒等映射，同时保留第 511 项的高地址映射。修改后，内核能够进入 `kern_init()`，完成页分配自检，持续打印时钟统计并关机。

这个问题提醒我：运行停在固件之后，不等于 Trap 处理函数一定有错。应按启动、分页、C 初始化、入口设置、中断处理的顺序定位，先确定程序实际执行到了哪一层。

临时副本使用了以下实际编码：

| 测试编码 | 作用 | 实际结果 |
| --- | --- | --- |
| `.2byte 0x9002` | 16 位压缩断点 | 返回到后续检查输出 |
| `.4byte 0x00100073` | 32 位断点 | 返回到后续检查输出 |
| `.2byte 0x0000` | 本平台下的 16 位非法编码 | 返回到后续检查输出 |

`logs/extra.log` 中四项均为 PASS。该副本还切换到 Best-Fit 并通过原有分配自检，之后继续处理 1000 次时钟中断并正常关机。正式项目仍保留默认分配器及原始初始化流程。

### 4. GDB 中观察 TrapFrame 与返回

调试时，在 `__alltraps` 执行 `SAVE_ALL` 前记录原 sp 和寄存器，随后在 `trap` 指令入口取得 a0 指向的帧，再运行到 `__trapret` 和恢复后的返回位置。实际观察如下：

| 检查项 | 观察值 |
| --- | --- |
| `sizeof(struct trapframe)` | 288 |
| 原 sp 减去帧地址 | 288 |
| 第一次时钟中断的 `frame->cause` | `0x8000000000000005` |
| 帧中 sp、t0、ra、s0 与记录值比较 | 均为 1 |
| 进入处理前的 ticks | 0 |
| 到达 `__trapret` 时的 ticks | 1 |
| 返回原 PC 后 sp、t0、ra、s0、a0 与记录值比较 | 均为 1 |

这些观察说明帧地址、保存偏移、计数行为及恢复路径在被测场景中一致。评分和补充测试通过并不等于已经验证任意嵌套 Trap、用户态切换、浮点/向量状态或所有异常恢复；这些都超出当前实现和测试范围。

## 六、重要实验知识点与 OS 原理的对应关系

### 1. 中断、异常与统一 Trap 入口

OS 原理中的中断通常指异步事件，异常通常与当前执行的指令同步关联。本实验用统一入口接收两者，再根据 `cause` 分流：时钟属于中断，非法指令与断点属于异常。统一入口使上下文管理可以复用，但不同事件仍需要不同处理和返回策略。

### 2. TrapFrame、函数调用现场与进程上下文

三者都涉及保存执行状态，但保存目的和范围不同。普通函数调用可以依赖 ABI 对调用者保存、被调用者保存寄存器的分工；异步中断无法要求被打断代码提前保存临时寄存器，因此本实验在入口统一保存整数寄存器。进程切换还要关联进程身份、调度状态、地址空间等信息，不能只靠一个 TrapFrame 完成。

本实验从处理函数返回后继续同一个内核执行流，没有创建或切换进程。Trap 上下文保存为后续调度提供基础，但不等于已经实现调度。

### 3. 机制与策略的分离

汇编入口、帧布局和恢复宏提供“能够进入和返回”的机制；C 处理函数决定计数、输出、关机和异常跳过策略。这样的分层使底层保存逻辑能够服务不同事件，同时让处理策略以较易检查的 C 代码表达。两层之间通过 TrapFrame 和函数调用约定连接，接口的一致性是分层成立的前提。

### 4. 中断屏蔽与临界区保护

本实验通过中断使能位控制当前 CPU 是否接受相应中断，实验3的页分配接口也保留了保存、关闭和恢复本地中断状态的包装。这对应 OS 中保护共享状态免受本地中断重入的思路。

它与多核互斥仍有差异：关闭本地中断不会阻止其他 CPU 访问同一数据，也不能自动代替锁、原子操作或内存顺序约束。本次没有实现完整的多核同步。

### 5. 时钟中断与抢占式调度

周期性时钟可以给操作系统提供重新评估执行安排的机会，进而支持时间片、超时和睡眠唤醒。本实验完成了稳定触发和计数，只在规定时刻输出并关机；没有维护就绪队列，也没有在时钟处理函数中选择另一个进程。

因此，收到持续时钟中断是抢占式调度的一个基础条件，但仅有 ticks 递增还没有形成调度器。

### 6. 异常返回位置与异常语义

`epc` 的处理体现了 OS 对异常后续行为的决定。实验要求对断点和非法指令跳过后继续，验证的是正确定位下一条指令。对于可以修复的缺页，操作系统通常应建立映射后重试；对于无法恢复的用户程序错误，可能需要终止进程或传递异常通知。

所以，异常处理的核心不是统一执行“PC 加一个常数”，而是先确定该异常应重试、跳过还是终止，再实现对应动作。

## 七、OS 原理中重要但本实验尚未完整覆盖的内容

**进程与线程管理。** 进程控制块、线程栈、状态转换、创建退出和上下文切换，是组织多个执行主体的基础。本实验只有一个持续运行的内核执行流，没有构建这些抽象。

**调度与时间管理策略。** 时间片轮转、优先级、公平性、阻塞唤醒、超时队列及实时调度都需要在时钟机制之上维护状态和策略。本实验的时钟处理没有作出这些调度决策。

**高级虚拟内存。** 请求分页、缺页修复、写时复制、页面置换和交换，需要在页表、物理页和进程地址空间之间建立更完整的管理关系。本实验沿用了启动映射和页面分配基础，但没有实现这些按需管理机制。
