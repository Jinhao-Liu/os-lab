# Lab2 实验报告：物理内存管理

## 一、实验目标与整体逻辑

本实验的目标是让内核知道哪些物理内存能够使用，并逐步提供按页分配和按字节分配的能力。我对本章的理解是：先识别内存，再用描述符组织内存，随后实现不同的页面分配策略，最后在页面之上管理小对象。

初始化的主要调用顺序为：

~~~text
kern_init()
  ├─ dtb_init()：取得物理内存信息
  ├─ pmm_init()
  │   ├─ init_pmm_manager()：选择并初始化页面分配器
  │   ├─ page_init()：建立描述符，排除已占用区域
  │   │   └─ init_memmap()：把完整空闲页面交给分配器
  │   └─ check_alloc_page()：执行当前分配器的自检
  ├─ slub_init()：初始化对象缓存
  └─ slub_check()：检查对象分配与释放
~~~

完成初始化后，页面通过 alloc_pages()/free_pages() 分配和释放；对象通过 kmalloc()/kfree() 分配和释放。First-Fit、Best-Fit 和 Buddy 是可以替换的底层页面分配策略，SLUB 则是建立在页面分配器之上的一层。

项目分工：刘晋豪 2510670 物理内存探测与页描述符初始化，Best-Fit 连续物理内存分配算法；李佩霖 2510547  Buddy System；徐乙涵 2512739 SLUB 算法

本框架每页为 4096 字节。物理地址是 RAM 中的位置，虚拟地址是内核访问内存时使用的地址，物理页号是物理地址除以页大小得到的编号，Page 指针则指向一条管理信息。它们不能混用。拿到一个 Page 指针后，还需要通过 page2pa() 得到物理地址，再加上映射偏移才能访问页面内容。

struct Page 中，ref 表示引用计数，flags 保存状态，property 记录块大小，page_link 用于串接链表。PageReserved 表示该页不能参与普通分配；PageProperty 表示该页是一个空闲块的首描述符。它们是两个不同含义的标记。“没有空闲块首标记”也不等于“这个页面一定是一个独立的已分配块首”。

pmm_manager 通过函数指针统一 init、init_memmap、alloc_pages、free_pages、nr_free_pages 和 check。上层使用相同接口，可以替换底层分配算法。
## 三、练习一：物理内存探测与页描述符初始化

### 3.1 Spec 的设计

本练习的输入是设备树解析结果及框架中的地址布局；函数无参数、无返回值。成功后的状态是 va_pa_offset、npage 和 pages 正确，所有可管理页面都有描述符，且分配器只接收到排除 OpenSBI、内核镜像、描述符数组及对齐空隙后的完整空闲页。

我在 spec 中明确以下边界：内存基址或大小为零、基址加大小溢出、内存不能覆盖内核、描述符空间不足时终止初始化；可管理上界不能超过 PHYSICAL_MEMORY_END；内存末尾向下对齐，空闲区起点向上对齐；如果最后没有完整空闲页，就不调用 init_memmap()。

### 3.2 核心函数的理解

page_init() 首先调用 get_memory_base()/get_memory_size()，检查信息并打印设备树报告的内存范围。设备树的 memory 节点通过 reg 属性描述内存起点和大小。
随后设置固定的虚实地址偏移，将物理上界限制到框架支持的范围，并向下对齐。这里最容易混淆的是 npage：它是可管理物理页号的排他上界，并非本机 RAM 的页面数量。描述符数量为 npage - nbase，转换关系为：

~~~text
物理页号 = 物理地址 / PGSIZE
Page 数组下标 = 物理页号 - nbase
物理地址 = (Page 数组下标 + nbase) * PGSIZE
~~~



pages 是描述符数组的内核虚拟地址，放在链接符号 end 之后的第一个页边界。计算它占用了多少物理内存时，必须先用 PADDR(pages) 转成物理地址。初始化时先把全部描述符标为保留，并清零引用计数和块大小。这样，只有后续明确登记的区域才会变成空闲页。

最后计算“描述符数组物理末尾向上取整到页边界”的位置 freemem。仅当 freemem 小于可管理上界时，才把 [freemem, maxpa) 对应的描述符交给 init_memmap()。因为内核加载在 OpenSBI 之后、描述符又位于内核末尾之后，这个起点自然排除了这些占用区域。

## 四、First-Fit 的理解与 Best-Fit 的实现

### 4.1 First-Fit 如何管理物理页

default_init() 建立空的循环双向链表，并将空闲页总数 nr_free 置零。它只是初始化管理结构，还没有把任何物理页加入空闲池。

default_init_memmap(base, n) 接收一段连续可用页对应的描述符，清除保留状态、块大小和引用计数，把首描述符的 property 设为 n，并设置空闲块首标记，再把它按地址顺序加入空闲链表。链表的一项代表一整块连续空闲页，不是每一页都占一项。

default_alloc_pages(n) 从链表头开始查找，找到第一个 property 至少为 n 的块就停止。如果块正好够用，就整个取走；如果更大，就返回前 n 页，把剩余部分作为新的空闲块留在原来的位置，最后减少空闲页计数并清除分配块首的空闲标记。若总空闲页不够，或者没有足够大的连续块，就返回 NULL。

default_free_pages(base, n) 先恢复这段页面的空闲状态，再按地址顺序插入链表。随后判断它是否与前块、后块物理相邻：前块末尾等于当前块起点时先向前合并，合并后再检查后块。合并时累加 property 并移除多余链表节点，保证一块连续空闲区域用一个块首描述符表示。


### 4.2 Best-Fit 的 Spec

Best-Fit 的接口和页状态约定沿用 First-Fit，但选择策略改为：遍历空闲链表，选择所有足够大块中最小的一块；存在恰好满足请求的块时即可停止。大小相同的候选保留先遇到的一个，不要求复杂的数据结构。

需要自行定义内部 free_area、各个管理函数及 best_fit_pmm_manager，并保持原有 basic_check() 和 best_fit_check() 不变。初始化、分割、回收、前后合并和空闲页计数都必须完整；分配失败不能修改状态。测试使用的 free_list、nr_free 约定需要保持一致。

### 4.3 核心函数的理解

best_fit_init() 清空链表和计数。best_fit_init_memmap() 解除新登记页的保留状态，然后复用回收函数完成元数据初始化、按地址插入和合并。

best_fit_alloc_pages() 扫描候选块，维护当前最小的可用块。找到结果后摘除节点，若有剩余则在原位置插入剩余块，最后扣减 n 页。仍以上述 8 页块和 3 页块为例，本算法会直接使用 3 页块，保留完整的 8 页块。

best_fit_free_pages() 按地址插入回收块，先合并前块，再合并后块。虽然分配时比较的是块大小，但链表仍按地址排序，这样更容易判断邻接关系。best_fit_pmm_manager 将这些函数注册到统一接口中。

### 4.5 两种算法的改进空间

First-Fit 可以使用 Next-Fit，从上次查找结束处继续扫描，减少反复扫描链表前端；也可以按大小分组以缩短查找，但会增加维护成本。及时合并相邻空闲块可以减轻外部碎片，不过不能消除所有碎片。当前按地址排序的链表查找、插入最坏都需要遍历多个节点。

又一个相关的问题上：按地址插入时，尾插分支执行 list_add() 后没有立即 break，循环可能继续处理刚插入的节点，造成重复插入或链表异常。这个问题属于框架已有代码，本次报告编写没有改动它；Best-Fit 的实现采用“找到插入位置后统一插入一次”的写法避开了该问题。

Best-Fit 也有改进空间。目前为了找到最小合适块，通常要扫描整条链表。可以额外建立按大小组织的索引或分档链表，提高查找效率，但释放、分割和合并时需要同步维护索引。它还可能留下难以再使用的小块，因此“本次剩余最少”并不保证长期碎片最少。

## 五、练习三：Buddy System 伙伴系统

### 5.1 Spec 的设计

Buddy 复用 pmm_manager，保持 Page 布局不变，从零新增分配器和测试。每阶一条空闲链表，第 k 阶块含 2^k 页，按对应物理页数对齐。当前上界是 128 MiB，因此最大阶为 15。

初始空闲区域不一定按大块对齐、长度也不一定是 2 的幂，需要分解成多个合法块，不能丢掉剩余完整页，也不能跨过保留页。申请 n 页时向上取整到 2 的幂；例如 3 页实际占用 4 页，5 页实际占用 8 页，统计按实际占用量变化。

释放接口传入原申请页数 n，整个取整后的块一次归还，不支持部分释放。实现通过 n 对应的阶数与块首记录的大小进行核对，因此不会额外保存原始 n，也无法区分同属一阶的不同请求数。零页申请等非法调用用断言拒绝，合法但过大的申请返回 NULL。

### 5.2 核心函数的理解

buddy_init() 初始化各阶链表和总计数。buddy_init_memmap() 清理描述符，再根据当前起点的物理对齐和剩余页数，选出可以放下的最大阶块并逐个登记。

buddy_alloc_pages() 求出申请对应的阶数，从这一阶开始向上找非空链表。找到大块后不断一分为二，一半继续拆分，另一半放入下一阶链表，直到达到所需阶数。分配块首的 property 保留实际页数，但清除 PG_property，表示它已被占用。

buddy_insert_free_block() 负责合并。伙伴的物理页号通过“当前物理页号异或块页数”求得。只有伙伴在边界内、未保留、是空闲块首且大小相同时才能合并，并继续尝试上一阶。物理上相邻的两块不一定是伙伴，例如对齐八页区域中的第 1、2 页彼此相邻，但它们的伙伴分别是第 0、3 页。

buddy_free_pages() 校验块首、大小和对齐，清理整块描述符，增加实际空闲页数，再调用合并函数。不能直接把 First-Fit/Best-Fit 中“释放分配块一部分”的测试套到 Buddy 上，因为二者约定不同。

## 六、练习四：简化 SLUB 对象分配器

### 6.1 Spec 的设计

第一层复用现有物理页分配接口，第二层提供 slub_init()、kmalloc(size)、kfree(ptr)。小对象按 16、32、64、128、256、512、1024、2048 字节分档，一个 slab 使用一页；大于 2048 字节的对象直接申请连续页。这里“任意大小”表示调用者可以传入不同的字节数，不表示底层恰好只消耗所申请的字节数。

返回地址保证 16 字节对齐。零字节、大小计算溢出或内存不足时返回 NULL，kfree(NULL) 无操作。其他释放参数必须是尚未释放的 kmalloc 原始返回指针。实现面向单 hart，不支持多核并发和任意非法指针检测。最后一个对象释放后，整页立即归还底层。

### 6.2 核心模块的理解

struct slub_cache 记录本档对象大小、每页对象个数和 partial 链表。struct slub_page 位于页首，记录所属 cache、对应 Page、空闲对象链表、在用对象数等信息。当前 64 位布局的页首元数据按 16 字节对齐后占 64 字节。

slub_init() 初始化各档 cache。kmalloc() 对小对象选择能容纳它的最小档位：例如申请 24 字节使用 32 字节档，申请 33 字节使用 64 字节档。优先从已有 partial slab 取对象；没有时才向 Buddy 申请一页，在页内切出对象并建立空闲链表。空闲对象自身的开头存储下一对象指针，不需要为每个对象另建一个 Page 描述符。

取走最后一个空闲对象后，该页移出 partial 链表。kfree() 将对象放回页内链表；如果原来是满页，则重新加入 partial；如果在用数变为零，则移出链表并释放整页。这几个状态转换决定了空间能否正确复用和回收。

大对象需要把页首元数据一起计入大小，再向上按页取整。比如申请 4032 字节，加 64 字节元数据恰好一页；申请 4033 字节就需要两页；申请 8193 字节需要三页，由 Buddy 实际提供四页。页首保存传给底层的请求页数，释放时使用相同请求数，由 Buddy 完成对应的整块归还。

kmalloc 返回的是可以访问的虚拟地址。kfree 对原始返回指针按页向下取整，找到本分配的页首元数据，再区分小对象和大对象的回收路径。

## 七、AI 辅助实现中的问题与解决过程

### 7.1 开启分页后发生取指页故障

早期 QEMU 启动没有进入正常内核打印，异常日志出现 exec_page_fault，故障 PC 包括 0x80200038。这个位置处在启动汇编中，说明程序还没有执行到物理页分配器，不能直接把故障归因于 Best-Fit 或 Buddy。

检查 entry.S 后发现：原启动页表只有高位内核映射。写入 satp 开启分页之后，CPU 还在物理加载地址附近执行几条指令，尚未跳到高位地址，因此缺少该地址的过渡映射。

解决方法是在启动页表补上覆盖 0x80000000 的恒等映射，保留原有高位映射，使 CPU 能继续取指并跳入高位内核。修复后重新交叉编译并正常启动 QEMU，才能继续验证分配器。这个问题属于启动框架的映射缺口，不是凭修改算法测试规避的。

### 7.2 宿主机检测器对旧 offsetof 写法报错

宿主机验证复用框架的链表宏时，旧 offsetof 宏使用基于空指针成员地址的表达式，UBSan 会对此报告问题，干扰对算法本身的检查。

解决方法是只在宿主机测试夹具里用 __builtin_offsetof 替换该宏，正式内核源码中的算法和链表实现保持不变。随后重新运行检测器，Buddy 测试没有 UBSan 诊断，SLUB 测试没有 ASan/UBSan 诊断。不能简单关闭检测器后就宣称没有问题。

### 7.3 提示词中必须明确的状态约定

只要求 AI“实现 Buddy”会留下申请数与实际占用数、如何找伙伴、是否允许部分释放等歧义；只要求“实现 SLUB”也可能遗漏大对象元数据和满页回收状态。因此最终 spec 和 prompt 明确了这些约定，并加入相应测试。

这些是设计时识别并通过约束预防的风险，不把它们写成已经发生并修复过的算法 bug。现有验证记录能够确认的主要故障是启动映射和测试适配问题；最终测试没有发现新的 Best-Fit、Buddy、SLUB 功能失败。

## 九、重要知识点及其与 OS 原理的对应

| 实验知识点 | OS 原理中的含义 | 关系与差异 |
| --- | --- | --- |
| 设备树获取 RAM 范围 | 内核启动时识别可用硬件资源 | 实验从框架的单段信息开始；实际系统还需处理多个区间、保留区和不同固件接口 |
| Page 描述符 | 用元数据记录页框状态 | 它描述物理页，不是页表项；页表项主要负责地址映射和访问权限 |
| 虚拟地址与物理地址转换 | CPU 通过地址转换访问物理内存 | 本实验使用固定内核映射偏移；一般进程的虚实地址并非都能直接相减转换 |
| 保留区域与页对齐 | 保护系统占用空间，并以页框为单位管理 RAM | 描述符本身也占 RAM，必须先扣除；对齐产生的不足一页空间不能作为完整页分配 |
| First-Fit、Best-Fit | 可变大小连续区域的选择策略 | 本实验以物理页数为粒度，体现查找、分割和相邻合并，而不是用户进程的完整堆管理 |
| 外部碎片 | 空闲空间分散，合计够大却无法满足连续请求 | 相邻块合并可缓解；Best-Fit 不保证碎片最少，也不能合并被占用页隔开的空洞 |
| Buddy 的分阶与伙伴合并 | 通过规则化块大小简化分割和合并 | 只合并真正的伙伴；申请向上取整会产生内部碎片 |
| SLUB 的对象缓存 | 在页内复用小对象，减少小额申请的整页浪费 | 本实验用大小档位体现主要思想，仍有档位取整、元数据和页内剩余空间的开销 |
| 状态恢复与资源回收 | 分配和释放应保持资源总量与管理结构一致 | 计数恢复只是必要检查，还要检查不重叠、数据隔离和链表状态，避免只看数字通过 |


## 十、OS 原理中重要但本实验尚未实现的内容

1. **进程地址空间与内存保护**：不同进程需要独立映射和访问权限。本实验主要管理内核可用物理页，没有建立完整的进程地址空间。
2. **按需分页和缺页处理**：进程首次访问未映射页面时，由缺页异常触发分配或加载。本实验在启动时组织物理页，不包含按需分配机制。
3. **页面置换与交换**：物理内存不足时，操作系统需要选择页面换出并在以后换入。本实验分配失败返回 NULL，没有换页策略。
4. **写时复制与共享页面**：多个地址空间可暂时共享页框，写入时再复制。框架虽有引用计数，但当前分配实验没有实现这些完整语义。
5. **多核同步与中断安全**：共享空闲链表需要防止并发修改。本实验按单 hart 执行，没有加锁或每 CPU 缓存。
6. **NUMA、DMA 与内存区域管理**：实际系统可能按节点、设备寻址范围和用途选择不同内存池，本实验只处理一个主要 RAM 管理范围。
7. **内存回收与压缩整理**：系统可回收缓存、迁移可移动页面以形成连续大块。本实验只合并已经空闲且满足条件的块，不迁移已分配页面。
