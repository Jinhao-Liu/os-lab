# Lab2 思考题

## 1. OS 不知道物理内存范围时，如何获取？

可以让固件或引导程序把内存布局告诉 OS，而不是由 OS 随意读写地址来猜测。

本实验使用设备树：启动时获得 DTB 地址，读取 memory 节点的 reg 属性，得到 RAM 的起始地址和大小，再扣除 OpenSBI、内核和管理数据占用的区域，剩余完整页才可以分配。[Devicetree 规范](https://devicetree-specification.readthedocs.io/en/stable/devicenodes.html#memory-node)

其他平台也可以使用固件提供的内存映射，例如 UEFI 的 GetMemoryMap。关键是既要知道哪里是 RAM，也要知道哪些区域已被保留，不能把所有能访问的地址都当作空闲内存。[U-Boot 的 UEFI 内存映射接口说明](https://docs.u-boot-project.org/en/latest/api/efi.html)

## 2. First-Fit 如何初始化、分配、回收和合并？有何改进空间？

- **default_init()**：建立空闲链表，将空闲页总数清零。
- **default_init_memmap()**：初始化可用页的描述符，在块首记录连续页数，并按地址顺序加入空闲链表。
- **default_alloc_pages(n)**：从头查找第一个不少于 n 页的空闲块。正好够用就整个取走；更大就分出 n 页，剩余部分继续留在链表中，同时减少空闲页计数。
- **default_free_pages(base, n)**：把页面按地址插回链表，检查与前后空闲块是否物理相邻，能连接就合并，并恢复空闲页计数。

**有改进空间。**链表很长时查找较慢，可以采用 Next-Fit，从上次查找位置继续；也可以按块大小分组。及时合并相邻空闲块可以减少外部碎片，但不能消除所有碎片。

当前 default_pmm.c 的尾插分支还缺少插入后的 break，可能重复处理新节点；这是正确性问题，应与性能优化分开看待。实验报告中已说明，现有 Best-Fit 使用统一插入一次的方式处理这一边界。

## 3. Best-Fit 是否有进一步改进空间？

**有。**当前实现通常要遍历所有空闲块才能找到最小的合适块。可以增加按大小组织的索引或分档链表，加快查找，但维护会更复杂。

Best-Fit 还可能留下很小、难以利用的空闲块。因此，选当前最小的合适块不一定使长期碎片最少。本实验选择简单链表实现，优先保证分割、释放、合并和计数正确。
